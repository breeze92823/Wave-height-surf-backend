# Wave Height Surf — BACKEND (game server)

Frontend (3D client) lives at `../Wave-height-surf`. Colyseus + Mongo.

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { userId, username, pfp })`). Client-authoritative: the server only bounds/sanitises saves (`src/sanitize.ts`). `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable; guests (`guest-` ids) are never saved. `/health` for Legion; `/monitor` and the playground are dev-only.
- The client keeps NO progress in the browser: this server's Mongo doc is the player's only save. A guest's (or a serverless session's) progress lasts the page only. The client's `src/net.js` speaks the contract below (and `src/remotePlayers.js` draws the roster).
- Messages client -> server: `saveProgress` (the whole snapshot, debounced client-side), `identify` (`{ userId, username, pfp }` after a sign-in/out mid-session), `ride` (`{ riding, distance }`, a few times a second while on a wave; distance clamped 0..`DISTANCE_MAX`, 0 when not riding). Server -> client (private): `progress` (the saved doc, sanitized, plus `serverTime`), `noProgress` (new account, guest, or no database: the client keeps its fresh state and saves it), `serverError` (the save could not be read: saving stays off so it is never overwritten), `leaderboard`. Saves are ignored until the session's load has answered (`loaded`). A second live session on the same account is evicted. Roster (`PlayerState`): `username`, `signedIn`, `pfp` (Bloxity profile picture URL, http(s) only, max `PFP_MAX_LEN`, "" = none), `riding`, `distance` (metres this ride).
- Saved progress shape (`PlayerDoc`, mirrors the client's `game.js` `fresh()`; the client sends the same keys): `waveHeight`, `trophies` (Wins), `gems`, `rebirths`, `level`, `xp`, `swells[]` (purchases per `ECONOMY.swells` tier), owned/equipped pairs `boards`/`board` and `trails`/`trail` (the equipped id must be owned), `autoPaddle`, `autoDelete`, `boostUntil { skill, wins }` (epoch ms), `lastGift` (epoch ms), `bestDistance` (metres, `$max` so it never drops), `pets[] { id, kind, equipped }` (equipped capped at `petSlots`), `petSlots`, `petsSeen[]`, `nextPetId`, `eggs { "Shell Egg": n }` (reward eggs to open), `potions[] { id, type, mult, minutes }`, `potionOn { wave|wins|luck: { mult, until } | null }`, `nextPotionId`, `playSeconds`, `playtimeClaimed[]` (`ECONOMY.playtime` indexes), `daily { day, last }`, `quests { since, progress { id: n }, claimed[], bonus }`, `tutorialStep` (0..`TUTORIAL_STEP_MAX`), `lastSeen` (the client's snapshot time; it restarts the Playtime clock after `ECONOMY.playtimeReset` min away). Unlike some sibling games there is no server-authoritative spin wheel or daily calendar: the surf game's Daily Reward, quests and gifts run on the client clock and are saved like everything else.
- Leaderboards (`src/leaderboard.ts`, `test/Leaderboard.test.ts`): the plaza's four boards (`SOUTH.boards` in the client config). Top `LEADERBOARD_SIZE` saved players by each of `LEADERBOARD_STATS` (`rebirths`, `waveHeight` = board "wave", `trophies`, `bestDistance` = board "best"), read with find/sort/limit into one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS`; each player's own rank = countDocuments(stat > theirs) + 1 (null for guests / no score). Server -> client `leaderboard` { boards: { stat: [{ name, value }] }, ranks: { stat: n | null } }, sent after each load and to everyone every `LEADERBOARD_EVERY_MS` (room clock). `connectDb` creates a descending index per stat. The test fake supports just that find/countDocuments shape.
- Presence (`src/presence.ts`, `test/Presence.test.ts`): what the others draw in the world, relayed through the roster as sent, only bounded. Roster fields `x`/`y`/`z` (feet, metres), `yaw` (wrapped to -PI..PI), `speed` (m/s), `board`/`trail` (catalog ids matching `ID_PATTERN`, "" = none), `pets` (kinds joined by commas, at most `PRESENCE_PETS_MAX`), `world` (clients only draw players in their own world), `avatar` (Bloxity look JSON, at most `AVATAR_MAX_LEN`, never parsed). Messages `pose` { x, y, z, yaw, speed } (~10/s, bounds `POSE_BOUNDS`), `loadout` { board, trail, pets: [{ kind }], world }, `setAvatar` { avatar }; the join options may carry `pose`, `loadout` and `avatar` too.
- Trading (`src/trade.ts`, `test/Trade.test.ts`): pets change hands between two players in the same room (Bloxity has no trade API). Only signed-in players whose save has loaded may trade. Client -> server `tradeRequest` { to: sessionId }, `tradeAnswer` { from, accept }, `tradeOffer` { pets: [{ id, kind }] } (at most `TRADE_PETS_MAX`), `tradeAccept` { rev }, `tradeCancel`. Server -> client `tradeInvite` { from, name }, `tradeDeclined` { to, reason: declined|busy|unavailable|signin }, `tradeOpen` { partner, name }, `tradeUpdate` { rev, mine, theirs, myAccept, theirAccept }, `tradeDone` { give: [ids], get: [{ kind }] }, `tradeClosed` { reason: cancelled|left }. Invites last `TRADE_INVITE_MS`; mutual invites open at once. Any offer change bumps `rev` and clears both accepts; an accept only counts for the current `rev`. The server never edits saves: each client applies `tradeDone` and saves. Trades live in room memory and close when either player leaves or re-identifies.
- `src/constants.ts` bounds must cover the client's `src/config.js` (`ECONOMY`, `PET_KINDS`, `PETS`, `SOUTH.eggs`; Wave Height and Wins are bounded by `CURRENCY_MAX`, 1e33). Egg names are display names with spaces (`NAME_ID_PATTERN`), every other id is an `ID_PATTERN` slug. A contract change goes in both projects.
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev` (build, `npm test`, and a check that `ROOM_MAX_CLIENTS` is 2-100); pushes also build+push a GHCR image and deploy to Bloxity Legion (`main` = prod, `dev` = dev), sending `roomSize` = `ROOM_MAX_CLIENTS` read from `src/constants.ts` (no `seatCap`: the matchmaker sizes pods). Needs repo var/secret `LEGION_GAME_ID` (= `wave-height-surf`) and secret `LEGION_DEPLOY_TOKEN`. The frontend repo has its own `deploy.yml` (build on PRs, upload to Bloxity Hosting on push).
